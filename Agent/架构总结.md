# CardSandBox 架构总结（面试用一页纸）

> 项目：Unity 2022.3 回合制 DBG 卡牌游戏（杀戮尖塔式），单人开发 18 个月，500+ 自有类，559 次提交。
> 定位：本文件是面试时的架构讲解底稿，按"总纲 → 主干 → 子系统"组织。

---

## 一、总纲：四段范式

整个战斗系统抽象为一条数据流 + 一条表现流，两流分离：

```
获取数据 → 修正数据 → 消费数据 → 动画编排
（Create）  （Modify）  （Apply）  （Sequence）
```

- **获取**：读配置（CardInfo/UnitInfo）创建运行时数据载体（`BattleCardCurrent`），静态工厂 `Create()`
- **修正**：Modifier 系统（buff/debuff/被动）通过 `GameModifyCenter.Modify(context)` 对同一份数据反复修正——这是核心，一份数据、多次修正、一次消费
- **消费**：结算伤害/治疗/状态，产出"这一下发生了什么"的结果
- **编排**：结算结果转 DOTween Sequence 演出，先算清楚再演出来

**本质**：数据流与表现流分离；数据与逻辑分离（数据只描述"是什么"，逻辑负责"怎么做"）。多态不是数据驱动的对立面，而是数据驱动内部丰富数据形式的手段（`[SerializeReference]` 多态数据 = 异构序列/树）。

## 二、主干一：GameModify 修正器引擎

```
Modifier（实例：数据 + 效果列表 + 计数）
   ↓ 注册到
GameModifyCenter.modifiers（全局字典）
   ↓ 任意数据节点需要修正时
GameModifyCenter.Modify(context)
   ↓ 遍历全局 modifier × modifierEffects
ModifierEffect<T>.Apply(modifier, context)  // is 判断路由，命中就改 context 数据
   ↓ 修正完成
写回载体字段 / 消费端只读结果
```

关键设计：

- **修正上下文 = GameEvent 子类**：`BattleCardModify_Cost`、`_Range`、`_ActiveEffectSettle` 等，每个上下文带完整定位信息（哪张卡/哪个 timming/哪个 atom/哪一段伤害），modifier 可精确筛选
- **修正粒度 = 全笛卡尔积**：每个 timming × 每个子效果(atom) × 每个伤害段/事件独立修正
- **节点自消费**：每个数据节点自带 `Modify(pipeline)`，三步 = 建上下文 → `GameModifyCenter.Modify` → 写回自己；顺序编排权在上层节点，不埋进节点内部
- **次序语义**：modifier 遍历无序，"只取最后一次修正"用 `SortedWeight.MaxOrDefault` 权重裁决；`modifyList` 仅作审计记录
- **计数器**：modifier 自身统计使用次数，修正计算保持纯函数（刷新会因选目标/手牌变动反复触发），消耗只在真结算点执行

## 三、主干二：GameFlow / RootGameFlow / GameAnimFlow

DOTween Sequence 的全局编排体系，替代前作的 async/await 链：

- **GameAnim**：基础动画原子（`GameAnim.AutoPlay(name)` 带日志追踪）
- **GameFlow**：Sequence 串行队列——入队 / 播放 / 完成自动释放
- **RootGameFlow**：唯一入队编排入口，控制流绑定动画完成回调，无兜底 = fail-loud（有意设计，问题立刻暴露而非静默吞掉）

控制流（回合推进、出牌结算）与动画播放在时序上咬合：逻辑入队 → 动画播完回调 → 推进下一步。

## 四、战斗系统（GameBattle）

### 回合结构

```
PlayerRound → EnemyRound → RoundEnd 三阶段循环
BattlePhase 抽象：Start / End / Modify 三类节点
```

### 出牌链路（必背）

```
BattleCardInteractive_Hold/Choice.OnPointerUp（只产目标）
  → 费用结算 → 移堆 → TimmingSys.Apply
  → SkillAtom.EffectApply：先遍历事件（ModifierCreationRequest 加 buff）再遍历伤害段
  → BattleUnit.TakeEffect(List<ActiveEffectResult>)
  → 死亡/胜负判定 → GameModify.Settle/Refresh → 手牌刷新
  → GameSeqFlow.Enqueue（动画编排）
```

### 效果模型（数据驱动）

```
CardInfo（SO 配置，[SerializeReference] 多态行为）
  → BattleCard + BattleCardCurrent（[JsonIgnore] 运行时修正结果缓存，不落盘，可重建）
  → BattleCardTimmingSys → BattleTimming（时机）→ SkillAtom（子效果）
      → EventAtom 多态序列：EffectAtom（伤害段：value/playTime/effectEnum）
                            ModifierCreationRequest（加 buff）
  → 修正后结果链：EffectAtom → ActiveEffectResult（caster 级）→ PassiveEffectResult（target 级，受击时即时修正）
```

分层要点：caster 级修正 = 白板终值进 `current`；target 级修正 = 每次受击/预览即时计算。原始配置只作修正器输入，消费端零依赖原始数据。

### 意图 AI（UnitIntention）

两步流水线：

```
筛选（IntentionCondition 过滤出候选集合）
  → 加权随机（WeightedRandomSelector 前缀和 + 二分查找）
```

条件与权重都是数据，都可被 Modify 修正——buff 能动态改变 AI 行为倾向。意图数据与 UI 展示分离（`BattleUnitSkill` 携带 `UnitSkillAtom` 直连意图 UI）。

## 五、工程基础设施

| 模块 | 方案 | 要点 |
|---|---|---|
| 管理器层 | 纯 C# Manager 管 Mono 插槽 | `GameXxx`（[Serializable] C# 类：Instance/Create/GetObj 懒加载/静态 API）管 `XxxObj`（Mono 纯插槽：序列化字段 + 纯 UI 操作，无业务逻辑）；生命周期自控，可脱离 Unity 单测 |
| 配置库 | 自研 JSONL（替代 Luban） | 一行一条记录、同 key 后写覆盖、`.old` 备份瘦身；Newtonsoft `TypeNameHandling.Auto` 多态还原 + `SpriteJsonConverter`；`InfoCreator<T>` Odin 编辑面板（刷新/写入/瘦身一键、行级错误定位） |
| 资源 | YooAsset 2.1.2 | 异步加载、对象池、Editor 模拟 / Standalone 离线包双模式 |
| 存档 | GameSerialize | 逻辑数据与表现分离；`BattleCard.current` 等运行时修正结果 `[JsonIgnore]` 不落盘 |
| 序列化约束 | Unity 原生不支持 Dictionary | 配置侧用 List，运行时 Create 翻译成 Dictionary，消费端 TryGetValue |
| 序列化环 | 持久对象自包含 | 环引用只在持久对象上是问题，即抛瞬态对象（管线）自由耦合；断环手段 = 改属性/NonSerialized/SerializeReference |
| 多语言 | GameLanguage | CN/EN/JP 配置动态切换 |
| 编辑器工具 | StoryLinker（GraphView+Odin 剧情节点编辑器）、GameTest（测试模式直跳战斗/剧情/场景） | |
| 调试 | GameDebug | 运行时开关 + 500 条循环日志缓冲，Build 中玩家可开启导出，零开销 |
| 日志/规范 | Agent 知识库 | JSONL 数据库记录所有决策/修Bug/复盘，与代码同提交 |

## 六、架构判据（取舍原则）

**内容 > 可读 > 性能**。加一种新效果/改数值谁最快最不易出 bug 是第一位；卡牌游戏性能是伪问题。多种实现输出相同时，选改动最小、最符合直觉的，不为架构优雅而重构。

**数据驱动 vs 多态的判据**：差异是参数 → 数据；差异是行为 → 多态（默认）。真正的敌人是耦合，不是多态。

## 七、演进线（为什么长这样）

本框架非教程搬运，是带着前作痛点自研推导的：

- **CardQuest（2023）**：MonoBehaviour 中心 + 数值硬编码内联 + async/await 动画链，战斗核心未走通
- **GameFramework（2024）**：前后端分层抽象尝试
- **SandBox_Card（2025-26）**：数值硬编码 → 修正器管线；async 链 → GameFlow Sequence 队列；Mono 上帝类 → 纯 C# Manager 插槽模式；Buff 图标 → Modifier 完整生命周期
